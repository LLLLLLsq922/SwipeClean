# SwipeClean 污渍系统可行性分析文档

| 项目 | 内容 |
|---|---|
| 文档名称 | 污渍系统可行性分析文档 |
| 适用产品 | SwipeClean（竖屏离线清洁解压游戏，Unity 6.3 / URP 17.3.0 / Android + iOS） |
| 分析对象 | 顶层相态 + 14 个二级子类 + 64 种物质清单 + 双向相变机制 + 溶剂标签体系 |
| 分析基线 | M1 已合并实现（`Assets/SwipeClean/Runtime/Cleaning/GpuCleaningSurface.cs` 等）与《SwipeClean MVP 详细设计与开发规格》（2704 行） |

| 结论 | **有条件可行**：架构与数据模型可行，相变机制可行，64 种物质全量需分阶段；主要风险集中在渲染纹理内存、每帧全屏 Pass 数量与内容量产工时 |

## 1. 结论摘要

总体判定：**有条件可行（Conditionally Feasible）**。本设计不推翻任何既有冻结决策，能在 M1 已有实现上以增量方式落地；但有 4 项硬约束必须先解决或先验证：状态纹理内存随层数线性增长、每帧全屏 Pass 数量随"层 × 操作"乘积增长、相变双向可逆的数值稳定性、64 种物质的内容量产工时。

| # | 关键维度 | 判定 | 依据（一句话） |
|---:|---|---|---|
| 1 | 数据驱动分类（Phase + 14 Subtype 兼容现有 6 类） | **可行** | `StainDefinition` 为纯 C# `record`（spec §5.4），新增 `StainPhase`/`StainSubtype` 与 `LegacyCategory` 映射不改变既有 `(ToolCategory, StainCategory)` 查找键，30 个类别组合零改动继续有效 |
| 2 | 效果矩阵规模（64 × 6 = 384 组合） | **可行但需降维** | 用"子类默认 + 变体覆盖 + 溶剂标签修正"三层降维，手写规则由 384 条降至约 50~65 条，其余由回退链求值 |
| 3 | GPU 通道复用 | **可行，无需双 RT** | R/G/B/A 已被质量/湿度/涂抹/水痕占用（spec §7.2）；相态改为"每层 CPU 标量 + 像素级由 G 导出"即可，避免双 RT 导致的 RT 内存翻倍（1024×8 层将由 81.3MB 升至 149MB，超 spec §16.3 的 70MB 预算） |
| 4 | `BrushOperation` 由 1 种扩到 6 种 | **可行，需改三处** | `BrushCommand` 已定义 6 种操作与 `LayerIndex`/`MoistureDeltaPerSecond`（`BrushCommand.cs` 已与 spec §7.4 一致），但 `GpuCleaningSurface.Enqueue` 第 85 行硬编码 `command.Operation != BrushOperation.Clean` 直接拒绝，`StainUpdate.shader` 仅有 Clean 语义，`FlushCommands` 无分组 |
| 5 | 相变机制（Dry↔Wet 双向可逆） | **可行** | 映射到既有 G（湿度）与软化公式（spec §8.3）与"回干"分支；相变不新增不可恢复状态，符合 ADR-009 |
| 6 | 风干/暖风机工具 | **可行** | 属既有 `BrushOperation.Absorb` 语义扩展 + 新增工具类别，`IToolStrategy`（spec §9.1）已支持 Begin/Apply/End/Cancel；但会增加一层"层 × 操作"Pass 需求 |
| 7 | 性能（每帧 Pass 数与像素吞吐） | **中等风险** | M1 单层最坏 3 次 Update Blit + 1 次 Composite（512² = 105 万像素/帧）；6 层 6 操作最坏约 31 次全屏 Pass（512² = 813 万像素/帧），必须真机实测 |
| 8 | 内容量产（64 种物质） | **需分阶段** | 按每物质 0.5~2 人日估算为 32~128 人日；拆为 12 → 24 → 64 三批，首批 12 种落在 M2 |

> **文档内勘误记录（v1.1）**
>
> 1. §2.1 与 §5.3 原写"归约链累计约 349,525 像素，为 512² 的 133%"，该数字与 `GpuCleaningSurface.CreateReductionChain`（第 217~230 行）的 9 级链不符。按 `size = Max(1, resolution/2)` 递推，正确值为 **87,381 像素 = 512² 的 33.3%**（`Σ 4^-k`，k=1..9），已在本版修正；§5.3 的吞吐结论由 13.1 Mpx/s 修正为 3.3 Mpx/s，占比约 1.6%，结论方向不变。
> 2. §5.3 原写"单层 1 次归约 = 8 次 Blit"，按 9 级链应为 **9 次 Blit**，已修正。

## 3. 技术可行性

### 3.1 枚举与数据模型扩展

**结论：不破坏既有 30 组合矩阵。**

新增两个枚举与一个映射表：

```csharp
public enum StainPhase { Dry, Wet }

public enum StainSubtype
{
    // Dry
    LoosePowder, SaltCrystal, SugarFilm, OilFilm, ProteinFilm, InorganicScale, InkPigment, AdhesiveResidue,
    // Wet
    LowViscosityLiquid, OilLiquid, ViscousPaste, AdhesiveGel, CompositeSludge, FastCureAdhesive,
}
```

兼容性论证：

1. **查找键不变**。spec §5.6 规定查找键为 `(ToolCategory, StainCategory, stainVariantTag?)`，优先级为"关卡覆盖 → 污渍变体 → 类别默认"。本设计将其扩展为 5 级回退链：
   `(Tool, Subtype+Tag) → (Tool, LegacyCategory, Tag) → (Tool, LegacyCategory) → (Tool, Phase 默认) → 内容错误`。
   前 3 级完全覆盖既有 30 组合，第 4 级为新增相态兜底，第 5 级为已有的"构建期拒绝"。因此现有 30 条规则**一行不改**即继续生效，构建验证仍可断言"30 个类别组合全部有明确规则"（`UT-TOOL-001`）。
2. **`LegacyCategory` 由子类唯一决定**，不存在二义性。映射表（与需求文档 §5/§6 一致）：

| StainSubtype | LegacyCategory | Dry 物质数 | Wet 物质数 |
|---|---|---:|---:|
| LoosePowder | Dust | 8 | — |
| SaltCrystal | Sugar | 5 | — |
| SugarFilm | Sugar | 7 | — |
| OilFilm | FingerprintOil | 7 | — |
| ProteinFilm | Sugar | 6 | — |
| InorganicScale | Dust | 0（保留位） | — |
| InkPigment | Dust | 3 | — |
| AdhesiveResidue | Sugar | 0（保留位） | — |
| LowViscosityLiquid | Water | — | 8 |
| OilLiquid | FingerprintOil | — | 4 |
| ViscousPaste | Mud | — | 8 |
| AdhesiveGel | Sugar | — | 2 |
| CompositeSludge | Mud | — | 5 |
| FastCureAdhesive | Sugar | — | 1 |
| **合计** | | **36** | **28** |

6. **溶剂标签体系**（与需求文档 §5 / §6 一致）：`-`（无需）、`acid`（酸性溶解：`stain_water_scale`、`stain_soap_scum`）、`degreaser`（去油：`stain_oil_cooking`、`stain_oil_machine`、`stain_hand_cream`、`stain_cleansing_oil`、`stain_fingerprint_oil`、`stain_face_cream`、`stain_sunscreen`、`stain_foundation`、`stain_lipstick`、`stain_nose_sebum`、`stain_cooking_oil_film`）、`enzyme`（酶解蛋白：`stain_milk_dry`、`stain_egg_dry`、`stain_egg_white`、`stain_finger_salt`、`stain_saliva`、`stain_pet_drool`）、`solvent`（有机溶剂：`stain_glue_white`、`stain_gum_residue`、`stain_sticker_glue`、`stain_slime_toy`）、`alcohol`（醇类：`stain_ink_dry`、`stain_marker_dry`）、`acetone`（丙酮：`stain_nail_polish`、`stain_super_glue`）。实现成本评估详见 §3.5。

3. **`StainDefinition` 字段扩展的兼容做法**。spec §5.4 已冻结 13 个字段。推荐**不修改既有 record 的字段顺序**，而是新增一个并列的纯数据记录：

```csharp
public readonly record struct StainPhaseProfile(
    StainPhase Phase,
    StainSubtype Subtype,
    float MoistureThreshold01,      // Dry→Wet 的软化阈值
    float SoftenDurationSeconds,    // 建议 1~3 秒（spec §8.3）
    float DryBackDurationSeconds,   // Wet→Dry 回干时长
    float PhaseMassRetention01,     // 相变后保留的质量比例（<1）
    float PhaseAdhesionGain01,      // 相变后附着增量（干膜更难擦）
    float CureWindowSeconds,        // FastCureAdhesive 时间窗；0 = 无时间窗
    float SolventTagMask            // 位掩码，见 §3.5
);
```

   并在 `StainDefinition` 之外维护 `StainSubtypeProfile`（14 条，每子类一条）与每物质的差异覆盖。这样做的收益：
   - 既有 13 个字段与既有测试断言不变；
   - 相变参数**按子类默认 + 按物质覆盖**，64 种物质不必各写 9 个字段；
   - `StainPhase` / `StainSubtype` 可由 `StainSubtypeProfile` 与物质记录共同推导，无需在 `StainDefinition` 中重复。

4. **内容 ID 与回退键**。材质 ID 形如 `stain_<material>`，子类配置 ID 形如 `subtype_<name>`，规则 ID 形如 `rule_<tool>_<subtype|category>[_<tag>]`。回退键统一为整数三键（枚举 + 枚举 + tag 枚举），**禁止用字符串拼接做运行时查找**（spec §16.2 要求 Playing 稳态 0 B/frame，字符串键会产生哈希与比较开销）。tag 用位掩码而非字符串：`None=0, Acid=1, Degreaser=2, Enzyme=4, Solvent=8, Alcohol=16, Acetone=32`，`SolventTagMask` 与 `RequiredSolventTag` 做按位与即可判定匹配。

### 3.2 相变机制到状态纹理四通道的映射

**结论：四通道够用，不需要双 RT。** 三备选方案的代价对比：

| 方案 | 通道分配 | 512×6 层 RT 内存 | 1024×8 层 RT 内存 | 代价与风险 |
|---|---|---:|---:|---|
| A. 通道复用（推荐） | R=质量、G=像素湿度、B=扰动/相态合并、A=水痕；相态=CPU 每层标量 + 像素级由 G 导出 | 20.5MB | 81.3MB | 需 B 通道编码方案（见下）；相态为"软"量，无二值跳变 |
| B. 附加 A 通道双 RT | 第二张 RT 存 `Phase01` + `CureProgress` + 保留 | 40.9MB | 162.5MB | **1024×8 层直接超出 spec §16.3 的 70MB RT 预算**；每层每帧 Pass 数翻倍 |
| C. 纯 CPU 相态 | 纹理仅存 R/G，相态完全由 CPU 每层标量驱动 | 20.5MB | 81.3MB | 无空间局部性：边缘/斜面流挂（需求文档 §7.2 要求）无法表现；但作为降级档（Low）可用 |

方案 A 的 B 通道编码细节：`B = 0.5 * disturbance01 + 0.5 * phase01`。8 位量化的可分辨度为 1/255，故：
- 扰动 0~0.5 区间对应 0~127 级，足以表达 spec §7.2 的"涂抹/扰动强度，供材质和近似流动"；
- 相态 0.5~1.0 区间同样 0~127 级，足以表达"当前偏干 / 偏湿"的连续软化外观。
- 既有 `StainUpdate.shader:39` 写入的固定值 0.04（约 10 级）需替换为 `0.5 * influence * dt * rate` 形式的增量，量纲与 A 通道方案一致。

相态的**权威定义**为两层：

1. **每层 CPU 标量 `Phase01`**（`StainLayerRuntime`，见 spec §8.1）：驱动关卡逻辑、HUD、提示与统计，是玩法真值。
2. **像素级 `Phase01`**：由 G（湿度）与局部软化进度导出，仅用于表现层。导出函数必须是**连续、单调、无迟滞**的，例如 `phase01 = smoothstep(wetThreshold - band, wetThreshold + band, G)`。禁止使用带方向性的双阈值迟滞（会导致同一湿度值在上升沿和下降沿给出不同相态，破坏"双向可逆"的可解释性，并使玩家看到的画面状态与关卡逻辑不一致）。

**每像素质量与相态的耦合**：相变不应改变 R（质量）本身，质量只由 Clean/Smear/Push/Absorb 改变（spec §7.7 明确"扩散不凭空增加 R"）。相变只改变**效率乘子**：`MoistureModifier` 曲线（spec §5.6）由相态与软化进度共同调制，干膜在低湿时乘子被压低、湿软时抬升。这样"质量不因相变凭空变化"，符合 ADR-008 的加权清洁度口径，也避免清洁度因相变抖动。

### 3.3 `BrushOperation` 由 1 种扩到 6 种的影响

需改动的三处（均已定位到行）：

| 位置 | 现状 | 改动 | 成本 |
|---|---|---|---|
| `GpuCleaningSurface.Enqueue`（第 83~91 行） | `command.Operation != BrushOperation.Clean` 直接 `return false` | 改为按操作白名单校验（`Clean/AddMoisture/Absorb/Smear/Push` 入队，`Reveal` 走 `UvInspectionController` 不入队，与 spec §7.4 一致） | 约 10 行，低 |
| `StainUpdate.shader`（48 行，单 Pass） | 只有 `state.r = max(0, state.r - strength*influence*dt)` 与 `state.b += influence*0.04` | 增加 `_Operation` uniform + `_Stamp2` 数组 + 每操作分支；Smear/Push 需要邻域采样 | 约 120~180 行 HLSL，中 |
| `GpuCleaningSurface.FlushCommands`（第 108~136 行） | FIFO 每 16 条一次 Blit，无分组 | 改为稳定分组（见 §3.4） | 约 80 行，中 |
| `BrushCommandQueue` | 环形 FIFO，容量 256，`TryEnqueue` 溢出返回 `false` | **不改结构**；分组在出队侧完成（避免为 6 个操作各开队列导致 6 倍内存与容量分配问题） | 0，无 |

**Pass 组织建议：单 Pass + `_Operation` 动态分支（推荐），而非每操作一个 Pass。**

| 方案 | 优点 | 缺点 | 判定 |
|---|---|---|---|
| 单 Pass + `_Operation` 动态分支 | 与 spec §7.6 的伪代码一致（`StainUpdate.shader Pass(Clean/Wet/Absorb/Smear/Push)`）；变体数为 1；`CleaningShaderBuildGuard` 与 `TryValidateCleaningShaderInclusion` 无需改动 | 动态分支在低端 GPU 上可能两条路径都执行，需实测 ALU 开销；`#pragma target 3.0` 下分支粒度受限 | **推荐** |
| 每操作一个 Pass（5~6 个 Pass） | 无分支、可分别优化寄存器压力；Smear/Push 的邻域采样可独立控制 | `Shader.Find` 后需按 Pass Index 索引，`Graphics.Blit` 需改用 `_updateMaterial.SetInt` + 显式 `PassIndex`（或在 CPU 侧预取 Pass）；`ProjectConfigurator` 的 Shader 清单校验若按 Shader 粒度则不必改，但构建变体与编译时间上升；首次进入关卡可能触发多 Pass 编译卡顿（spec §16.4 加载预算 500ms 内完成 RT 初始化与预热的约束） | 备选 |
| 每操作一个独立 Shader 文件 | 隔离最好 | **必须同步登记为第 5~9 个 Always Included Shader**，否则 Player 构建后 `Shader.Find` 返回 `null`，`Initialize` 会走 `Debug.LogError` + 返回 `false` 路径（第 52~57 行），关卡进入 `AppState.FatalError` | 不推荐 |

选择单 Pass 的另一个理由：M1 已有 `MaxStampsPerBatch = 16` 与 `StainUpdate.shader` 的 `float4 _Stamp0[16]` 数组，若改为多 Pass 而不同时调整数组大小，会引入每 Pass 独立的 uniform 上传（`SetVectorArray` 16×4 float × 3 数组 = 768B/Pass，可忽略），但 Pass 切换本身在移动端有固定开销。

**批次上界推算**（512² 分辨率）：

| 场景 | Update Blit 次数 | Composite Blit 次数 | 全屏 Pass 合计 | 像素/帧 |
|---|---:|---:|---:|---:|
| M1 单层单操作（48 命令） | ⌈48/16⌉ = 3 | 1 | 4 | 1,048,576 |
| M2 目标：6 层 × 2 操作 | 12 | 6 | 18 | 4,718,592 |
| 最坏：6 层 × 6 操作（spec §7.6 要求每层每帧 ≤ `MaxPassesPerLayer`，默认 4） | 24（受限后） | 6 | 30 | 7,864,320 |
| 未受限最坏上界（不推荐） | 36 | 6 | 42 | 11,010,048 |

结论：必须在 `StainUpdateScheduler` 中实现 spec §7.6 的 `MaxPassesPerLayer`（默认 4），把最坏 42 次压到 30 次；否则 Low 档（30 FPS）的 GPU 预算会被单帧尖峰击穿。另外 `MaxCommandsPerFrame = 48` 与 `MaxStampsPerBatch = 16` 的组合意味着**每次 Blit 都至少消耗 16 条命令**，即 6 层 × 6 操作在 48 命令/帧的限制下最多填满 3 个 batch，其余操作在该帧不会有数据——这是天然的保护，但也意味着**多操作并存时命令会被延后到下一帧**，需确认延迟预算（spec §6.8 的输入延迟要求触点 <50ms，见需求文档 E12-002）不受影响。

### 3.4 多操作 / 多层调度与迁移路径

`StainUpdateScheduler` 的推荐实现（无分配、可预测）：

```text
每帧：
  1. 从 BrushCommandQueue 出队 ≤ MaxCommandsPerFrame 条（沿用 M1 上限 48）；
  2. 按 (LayerIndex, Operation) 写入预分配的桶：bucket[8][6]，每桶 ring buffer，
     桶内按 Sequence 自然有序（FIFO 出队已保证单调）；
  3. 对每个非空桶：SetInt("_Operation") + SetVectorArray(_Stamp0/_Stamp1/_Stamp2)
     → SetInt("_StampCount") → Graphics.Blit(layerStateRead, layerStateWrite, update)
     → swap(Read, Write)；层内桶按 Operation 的固定顺序执行，保证同帧内语义确定；
  4. 每层每帧 Pass 计数达 MaxPassesPerLayer 后，剩余命令保留到下帧（顺延，不丢弃）；
  5. 全层结束后统一调用一次 Composite（多层的排序在 Composite 内完成，
     而不是每层一次全屏 Blit）。
```

内存开销：`8 × 6` 桶 × 每桶容量（建议 = `MaxStampsPerBatch` = 16）× `BrushCommand` 结构大小（约 64B）≈ 49KB，可忽略。实现上更简的做法是**不做物理桶**，只做一次稳定排序（按 `LayerIndex` 主键、`Operation` 次序键、`Sequence` 次序键），排序对象是预分配的 48 元素数组，插入排序在近似有序时接近 O(n)，可满足 spec §16.2 的 0 B/frame。

迁移路径（保持 M1 可玩性不中断）：

| 步骤 | 内容 | 可独立验证的完成定义 |
|---:|---|---|
| S1 | 把 `_stateRead`/`_stateWrite`/`_composite`/归约链封装为 `StainLayerState`（数据+资源），`GpuCleaningSurface` 持有 `StainLayerState[]`（M2 先支持 1 层，接口按 N 层设计） | EditMode 断言 N=1 时行为与 M1 逐比特一致（同 512 分辨率、同 Stamp 序列） |
| S2 | `FlushCommands` 替换为 `StainUpdateScheduler`，但只注册 `Clean` 一个桶；引入 `MaxPassesPerLayer` | PlayMode 第 1 关手感与 M1 无差异；RT-008（Batch Ordering，spec §17.3）通过 |
| S3 | `StainUpdate.shader` 增加 `_Operation` 与 `_Stamp2`，先只实现 `Clean`/`AddMoisture`/`Absorb` 三个分支 | RT-002/RT-003/RT-004 通过 |
| S4 | `Enqueue` 放开操作白名单；新增 `ToolEffectResolver` 产出命令 | UT-TOOL-001/UT-TOOL-002 通过 |
| S5 | 启用 N 层 + Composite 多层排序 | RT-009/RT-010 通过；覆盖率按 `ObjectiveWeight` 汇总（复用既有 `CleanlinessCalculator`） |
| S6 | 实现 `Smear`/`Push`（邻域采样） | RT-005/RT-006 通过；R 总量守恒误差在业务容差内 |
| S7 | 相变（软化 + 回干 + 相态乘子） | UT-STAIN-001/UT-STAIN-003 通过 |

### 3.5 纯 C# `ToolEffectResolver` 与溶剂标签匹配

**核心障碍：`SwipeClean.Domain` 的 `noEngineReferences: true`。** spec §5.6 的 `ToolStainEffectRule` 直接写 `AnimationCurve SpeedModifier` 等三个字段，`AnimationCurve` 属于 `UnityEngine` 类型。若把该 record 原样放进 Domain，程序集将无法编译。

**适配方案（推荐：Baker 烘焙 + Domain 侧 LUT 结构）：**

| 层 | 类型 | 是否含 UnityEngine | 说明 |
|---|---|---|---|
| 内容源 | `ToolStainEffectAsset : ScriptableObject` | 是（Editor/Content 程序集） | 美术/策划在 Inspector 中编曲线，符合 spec §5.6 的作者体验 |
| Baker | `EffectMatrixBaker`（Editor） | 是 | 把每条规则的三条曲线按固定采样数 N 烘焙为 `float[N]`，写入纯数据资产 |
| 纯数据 | `struct CurveLut { float[] Samples; float Min; float Max; }` + `Evaluate(float x)` | **否** | 线性插值采样：`index = x*(N-1); i0 = (int)index; t = index-i0; return Lerp(s[i0], s[i0+1], t)`，域内 `Clamp01` |
| Domain 规则 | `readonly record struct ToolStainEffectRule(int Tool, int StainKey, int TagMask, float BaseEfficiency, CurveLut Speed, CurveLut Pressure, CurveLut Moisture, ...)` | 否 | 整数键，无字符串、无 UnityEngine |

采样数 N 的取值论证：曲线输入已被 Clamp 到 `[0,1]`（spec §5.6），使用 N=32 时最大插值误差为二阶导数量级；对手感类曲线（速度/压力/湿度修正）建议 **N=32**，对阈值型曲线（软化增益）建议 **N=64**。

内存：N=32 每条曲线 128B，一个规则 3 条 = 384B；65 条规则 ≈ 25KB（N=64 时约 50KB）。相对 spec §16.3 的 120MB 引擎/托管堆预算可忽略。

**采样成本**：`CurveLut.Evaluate` 为 1 次乘、1 次取整、1 次插值，约 5~8 条指令；一条完整效率公式（spec §5.6）含 3 条曲线 + 5 次标量乘，约 40~60 条指令。/48 条命令/帧 ≈ 2,900 条指令/帧，约 1~3µs，处于 spec §16.1 的"Tool/污渍规则 1.0ms 目标 / 2.0ms 上限"内，余量充足。

**溶剂标签匹配**（回答需求文档 §12 的开放问题：把 `acid`/`degreaser`/`enzyme` 做成喷雾档位而非独立工具）：

| 机制 | 判定 | 理由 |
|---|---|---|
| 溶剂做成**喷雾的档位**（`ToolRuntimeState.SolventMode`） | **推荐** | 不新增工具类别 → 不新增 `ToolStainEffectRule` 的 30 组合基线 → 6 类 × 5 工具 = 30 组合的构建验证不变；只需在 30 条规则中新增 6 个"溶剂修正行"（按 tag），改动量为 6 条而非 6×6=36 条 |
| 溶剂做成**独立工具**（+6 个工具） | 不推荐（M2/M3） | 工具数从 5 增至 11，类别组合从 30 增至 66，UI 工具栏需重排（spec §11.4 HUD 布局规则），`IToolStrategy` 实现从 5 个增至 11 个，切换耗时 ≤100ms 的验证面扩大一倍 |
| 溶剂做成**喷雾的一颗子弹式消耗品** | 备选 | 与 `ToolRuntimeState.ConsumableUsed`（spec §9.2）天然兼容，但会引入"用完了怎么办"的可恢复性设计问题，与 ADR-009 有张力 |

匹配规则：`RequiredSolventTag`（字符串，spec §5.4）与工具的 `EffectTags`（spec §5.5）在 Baker 阶段统一转为位掩码；运行时判定为 `(toolMask & stainRequiredMask) != 0`。`RequiredSolventTag` 为 `"-"`（无需）时掩码为 `0`，判定恒真。**注意**：`stain_nail_polish` 与 `stain_super_glue` 标记 `acetone`，而 `acetone` 在 spray 档位体系中是否存在，取决于产品是否允许"丙酮档"这一拟真内容；若不希望出现丙酮，可用 `solvent` 标签统一覆盖两者，代价是失去"指甲油 vs 速干胶"的差异手感。此点列为开放问题。

### 3.6 64 种物质 × 6 工具的效果矩阵规模控制

**结论：384 个组合绝不可手写。** 三层降维方案：

```text
第 1 层：类别默认（强制完整）   6 LegacyCategory × 5 基础工具 = 30 条   ← 已由 spec §5.6 冻结，零改动
第 2 层：子类默认（覆盖差异）   14 StainSubtype 中约 10 个需要显式规则 × 平均 1.8 工具 = 约 18 条
第 3 层：溶剂标签修正           6 个 tag × 平均 1.2 条 = 约 7 条
第 4 层：相态默认               Dry/Wet × 5 工具 = 10 条（兜底，仅用于无子类规则的组合）
--------------------------------------------
实际手写规则条数 ≈ 30 + 18 + 7 + 10 = 65 条
```

覆盖率验证：64 种物质 × 6 工具 = 384 个 `(Tool, StainId)` 组合，每个组合都由回退链在第 1~4 层中命中至少一条规则。构建期的 `ContentValidator` 必须**穷举 384 组合并断言全部命中**（而不是只断言 30 个类别组合），且同时断言：
- 无规则组合数为 0；
- 所有曲线输出有限（拒绝 NaN/Inf，spec §5.6）；
- 每个 `RequiredSolventTag != "-"` 的物质至少有一个允许工具能提供该 tag（spec §5.4 的验证规则）。

**降维后的边界情况**：
- `stain_super_glue`（FastCureAdhesive）需要与 `stain_glue_white`（AdhesiveGel）有不同手感，前者必须显式覆盖 `CureWindowSeconds`；
- `stain_nail_polish`（InkPigment→Dust）与 `stain_ink_dry`（InkPigment→Dust）同子类同类别，若要有差异只能靠**变体标签**（spec §5.6 的第 3 级查找键），即需要 2 条第 2 层规则，而不能靠子类默认；
- 因此"变体标签"机制不能被省略，它在 64 物质规模下从"可选优化"变成"必需的差异表达手段"。建议为每个物质预留一个 `variantTag` 字段（默认空），仅在需要表达差异时使用，预计实际使用 8~12 个。

### 3.7 相变数值稳定性与工程对策

| 问题 | 机理 | 对策 |
|---|---|---|
| 质量守恒（Smear） | 邻域采样在边界处取不到样本，直接导致总量减少（被误判为"擦除"） | 边界采用 **Clamp 采样**而非零采样；`CoverageReduce` 的均值按 Clamp 边界重复计入；构建期在 TestHarness 场景中执行 P2（6 层多工具 60 秒）并断言 R 总量漂移 ≤ 业务容差（建议 ≤2%） |
| 软化/回干振荡 | `softening += dt/softenDuration` / `-= dt/dryBackDuration` 在阈值附近随湿度噪声反复穿越（spec §8.3） | 采用**单调无迟滞的连续映射**替代二值开关：`targetSoftening = smoothstep(threshold-band, threshold+band, G)`，再对 `softening` 做一阶低通（`softening = Lerp(softening, target, 1-exp(-k*dt))`，k≈4~8）。该形式天然连续、可逆、无极限环 |
| 速干胶时间窗 | `FastCureAdhesive` 若在窗口内未处理就"固化"，与 ADR-009（不强制失败）冲突 | 时间窗只允许**放大难度（附着上升、效率下降）**，不允许**阻断完成**：窗口结束后仍可用 `solvent`/`acetone` 档 + 长时间擦拭清除。窗口必须在 UI 上有可读表达（软化进度条/光泽），不能只靠倒计时文本（spec §8.3 已明确"不以纯倒计时为唯一表达"） |
| 复湿死循环 | 玩家反复"喷湿 → 吹干 → 喷湿"，每次相变都损失质量并增加附着 | 相变乘子**有下界**：`PhaseMassRetention01 ≥ 0.35`、`PhaseAdhesionGain01` 单项累计上限 `< 1`，且每层的累计相变次数计入 `Revision`；超过 N=6 次后相变增益不再累加（饱和），保证任意操作序列下仍存在有限步完成路径 |
| 湿度溢出 | 连续喷雾使 G 长期饱和为 1，`MoistureModifier` 曲线失去意义 | G 的写入使用 `saturate`，同时引入 spec §8.4 的 WaterMark 机制作为超额湿度的出口（新增有效质量 ≤ 初始目标质量的 5%，上限 10%），把"过度喷雾"从无效果转化为有代价 |
| 相态与清洁度抖动 | 相变改变效率乘子 → 帧间清除量波动 → `Cleanliness01` 抖动 → 完成判定反复跨越阈值 | 复用既有防抖：`ObjectiveEvaluator` 的 `hysteresis01 = 0.002` 与"连续 2 次通过"（`ObjectiveEvaluator.cs:47`，spec §7.9）；UI 显示值使用阻尼插值（spec §7.8） |
| 初始质量基准错误 | M1 的 `_initialMeanMass` 由首帧异步回读赋值，玩家可能已开始擦拭 | 关卡加载流程中把"执行一次覆盖率归约并等待结果"作为 `Initialize` 的同步前置（spec §7.3 第 4 步已要求"执行一次覆盖率归约，保存每层 InitialMeanMass"）；加载预算中 RT 初始化与初始归约占 500ms（spec §16.4） |
| `DeltaTime` 上限 | 切后台/掉帧后单帧巨量变化 | 沿用既有 clamp：`BrushCommand` 构造器已 `Clamp(deltaTime, 0f, 1f/15f)`（`BrushCommand.cs:42`），`StainUpdate.shader:37` 亦 clamp 到 0.0666667。相变积分必须使用同一个 `DeltaTime`，禁止使用 `Time.deltaTime` 直通 |

## 4. 内容生产可行性

### 4.1 工时估算口径

按需求文档 §5 / §6 的 64 项清单，每项物质的生产内容拆为 5 类产出：

| 产出 | 内容 | 单物质工时 |
|---|---|---|
| 定义记录 | 13 个 spec §5.4 字段 + 子类与相变参数覆盖 + `variantTag` | 0.15~0.3 人日 |
| 遮罩资产 | 1 张灰度遮罩（512/768/1024 多分辨率）+ 拼接/旋转能力 | 0.3~0.8 人日（见 4.2 降本方案） |
| 视觉配置（VisualProfile） | 颜色、光泽、法线强度、湿度响应、软化表现 | 0.2~0.4 人日 |
| 音频标签（AudioMaterialTag） | 归类到既有 ≥4 组摩擦循环（AUD-001）或新增 | 0.05~0.15 人日 |
| 效果规则覆盖 | 差异化的第 2 层规则（仅约 10 项需要） | 0.2~0.5 人日（仅差异项） |
| **单物质合计（无差异项 / 有差异项）** | | **0.7~1.65 / 0.9~2.15 人日** |

即用户口径的"每物质 0.5~2 人日"成立，中位数约 **1.1 人日/物质**。

### 4.2 遮罩/贴图资产制作方式

**推荐：程序化噪声生成为主 + 少量手绘 + 不采样真实照片。**

| 方式 | 覆盖比例 | 成本 | 风险 |
|---|---:|---|---|
| 程序化噪声生成器（Editor 工具：Perlin/Worley/距离场 + 形状模板 + 参数种子） | 约 70%（灰尘、粉末、水渍、油膜、泥点等无固定轮廓类） | 一次性工具开发 3~5 人日；之后每物质 0.1~0.25 人日 | 需要保证"轮廓可辨识但不过度恶心"（需求文档 ART-002）；需固定随机种子保证可复现 |
| 手绘遮罩 | 约 20%（指纹、唇膏印、鸟粪、史莱姆等有特征轮廓类） | 每物质 0.5~0.8 人日 | 美术工时是内容量产的关键路径 |
| 采样真实照片 | **不建议** | — | 需求文档 E11-F03 / ART-006 要求原创或授权素材与来源清单；照片衍生遮罩的授权链条难追溯，且与 ADR 中"不做真实流体"的克制风格不一致 |

**共用原型（archetype）降本**：64 项物质可归入约 **10~12 个遮罩原型**（细粒散布、粗粒散布、结晶斑、糖膜、油膜、水珠、低黏液痕、黏稠膏痕、胶体滴、泥浆涂抹、墨迹、硬垢）。同原型下通过**缩放、旋转、密度、颜色、湿度响应**做差异。这样遮罩实际制作量从 64 张降到 12 张原型 + 52 次参数化变体。

### 4.3 与 ADR 的一致性

| ADR | 本设计的一致性 | 说明 |
|---|---|---|
| ADR-004（不实现 Navier–Stokes） | **一致** | 相变只改变湿度 G、软化进度与效率乘子，不引入速度场或压力求解；"边缘/斜面流挂"用 spec §7.11 的规则层（G + FlowFactor）与低频 Push pass 表现，属表现层，按画质降级 |
| ADR-006（布只有一套类，干/湿/饱和为运行时状态） | **一致** | 风干/暖风机作为**独立工具类别**（提供 `Absorb` 语义）而非"布的第二种形态"，不违反该 ADR |

## 5. 性能与内存可行性

### 5.1 状态纹理内存（计算依据：`4 字节/像素 × 分辨率² × 2（ping-pong）× 层数`）

单层单张 = `res² × 4B`；每层双缓冲 = `2 × res² × 4B`。另需计入**归约链**（M1 为 `res/2` 至 `1×1`，累计像素 = `res²/3 × (1 + 1/4 + 1/16 + …) ≈ res²/3`，故 2 张单分量纹理分摊后约 `0.33 × res² × 1B ≈ 0.22 × res²` 字节）：

| 分辨率 | 单层双缓冲 | 归约链/层（实测口径） | Composite（单张，按表面计） | 6 层合计 | 8 层合计 |
|---:|---:|---:|---:|---:|---:|
| 512 | 2.00 MB | 0.33 MB | 1.00 MB | **15.0 MB**（含 1 张 Composite） | **19.7 MB** |
| 768 | 4.50 MB | 0.75 MB | 2.25 MB | **33.8 MB**（含 1 张 Composite） | **44.3 MB** |
| 1024 | 8.00 MB | 1.33 MB | 4.00 MB | **60.0 MB**（含 1 张 Composite） | **78.7 MB** |

对照 spec §7.2 的内存表（只含层状态 ping-pong：512/2MB/12MB、768/4.5MB/27MB、1024/8MB/48MB），本表在计入归约链与 Composite 后，**1024×6 层 = 60.0MB 已接近 spec §16.3 的"状态 RT/归约 RT/临时 RT = 70MB"预算上限，1024×8 层 = 78.7MB 直接超预算**。

**若采用双 RT 方案（§3.2 方案 B），内存翻倍**：512×6 层 30.0MB、768×6 层 67.5MB、1024×6 层 120.0MB、1024×8 层 157.3MB —— 1024 档在任何层数下都不可接受。这是"通道复用优先"的量化依据。

**降本建议**：
- High 档（1024）层数上限从 8 **下调为 6**（与 spec §2.3 的"最大活跃污渍层 = 8"冲突，需主策/主程拍板，或改用下面的压缩方案）；
- 或者：把归约链从 RGBA32 改为 **R8 单通道**（归约只需要 R 通道），单层归约成本由约 0.33MB 降至 0.08MB，1024×8 层由 78.7MB 降至 67.4MB，勉强进入 70MB 预算；
- 或者：**6 层以上时把 Composite 降为半分辨率并上采样**（1024² → 512² Composite），节省 3MB 峰值，但会牺牲视觉锐度；
- 结论：**"1024 + 8 层 + 双 RT"这一组合在任何预算下都不可行；必须走通道复用 + R8 归约链。**

### 5.2 每帧 GPU Pass 次数与批次

计算依据：`Update Blit = ⌈每分钟层的操作命令数 / MaxStampsPerBatch(16)⌉`，受 `MaxCommandsPerFrame(48)` 与 `MaxPassesPerLayer(4)` 双重限制；`Composite Blit = 每帧 1 次`（多层在 Composite 内排序，见 §3.4）。

| 场景 | Update | Composite | 合计全屏 Pass | 512² 像素/帧 | 60 FPS 需像素率 |
|---|---:|---:|---:|---:|---:|
| M1 单层 Clean（实测口径） | 3 | 1 | 4 | 1.05 M | 63 Mpx/s |
| M2 三关目标（6 层 × 2 操作，命令量中等） | 12 | 1 | 13 | 3.41 M | 205 Mpx/s |
| 中负载（6 层 × 6 操作，每层 ≤2 Pass） | 12 | 1 | 13 | 3.41 M | 205 Mpx/s |
| 高负载（8 层 × 6 操作，每层 ≤4 Pass，受 MaxPassesPerLayer 限制） | 24~32 | 1 | 25~33 | 6.55~8.65 M | 393~519 Mpx/s |

结论：Low 档必须把 `MaxPassesPerLayer` 降到 2、`MaxStampsPerBatch` 降到 8（spec §2.3 的 Low 档配置）、`MaxCommandsPerFrame` 降到 32，并把 `MaxStampsPerBatch` 与 `MaxCommandsPerFrame` 从 `const` 改为**按 Quality 档注入的实例字段**（当前是 `private const`，见 `GpuCleaningSurface.cs:13-14`）。这是一项必须的改造，否则 spec §2.3 的档位矩阵无法落地。

### 5.3 覆盖归约链与异步回读

| 项 | M1 现状 | 多层后的影响 | 预算影响 |
|---|---|---|---|
| 归约频率 | `CoverageIntervalSeconds = 0.16f` → 6.25 次/秒（spec §2.3 的 Medium 档为 6Hz，基本对齐） | 单层 1 次归约 = 9 次 Blit（512 → 256 → … → 1）；6 层 = 54 次 Blit/次快照；每帧分摊约 0.55 次 Blit | spec §16.1 的"Coverage 调度/回调 0.5ms、GPU 1.0ms 均摊"可容纳 |
| 归约像素 | 每层 87,381 像素/次（512² 的 33.3%；9 级几何级数 256²+128²+…+1² = (4⁹−1)/3 = 87,381） | 6 层 = 0.52 Mpx/次；层数翻倍则归约总量翻倍，但**归约成本与层状态总像素成正比**，无法通过降频以外的办法压 | 每次快照 0.52 Mpx，6.25 次/秒 = 3.3 Mpx/s，相对 Update+Composite 的 205 Mpx/s 占比约 1.6%，可接受 |
| 回读并发 | 已有 `_coveragePending` 保证同一时刻最多一个请求（spec §7.8 的"同一时刻最多一个 GPU 回读请求"） | 6 层不能各发一个请求，必须**串行化**：把 6 层的 1×1 结果先汇总到一张 1×N 小纹理（spec §7.8 的"汇总为 1×N 小纹理"），再单次回读 | 这是必须在 S5 步骤实现的改造，当前代码回读的是单张 1×1 |
| 回读失败 | 已有 `_forceSynchronousCoverage` 同步兜底（第 153~163、174~180 行） | 同步兜底从 6.25Hz 降到 4Hz（spec §7.8：不支持时降为 4Hz），并且**每层同步 `ReadPixels` 会有 GPU 管线停顿**（M1 的 `ReadCoverageSynchronously` 会创建 1×1 `Texture2D` 并 `ReadPixels`，注意它在每次调用时都会 `new Texture2D`，多层化后必须改为复用一张常驻 1×1 纹理，否则违反 spec §16.2 的 0 B/frame） | 必须实测 GLES3 低端机的同步路径 |
| 回读到期时间 | 异步回读通常需 1~3 帧才回调 | 待机一致：`ApplyMeanMass` 使用 `requestGeneration` 校验过期请求（第 169 行），多层化后需把 generation 检查扩展为 per-layer revision（spec §8.1 的 `Revision`） | 已有机制可直接扩展 |

### 5.4 CPU 预算

spec §16.1 给出"Tool/污渍规则 1.0ms 目标 / 2.0ms 上限"（30 FPS 档）。本设计在该预算内的工作量：

| 工作项 | 单次成本估算 | 每帧次数 | 每帧合计 |
|---|---:|---:|---:|
| `ToolEffectResolver` 取规则（整数三键 → 稀疏数组/字典） | 约 50~150ns | 48（命令数） | 2.4~7.2µs |
| 效率公式（3 条 LUT + 5 次标量乘） | 约 40~60 条指令 | 48 | 约 3µs |
| 相态积分（每层 `softening` 一阶低通） | 约 20~40 条指令 | ≤8 层 | 约 0.5µs |
| 溶剂标签位掩码匹配 | 约 5ns | 48 | 0.24µs |
| 覆盖率回调（清理度加权汇总） | `CleanlinessCalculator` 已在 Domain，O(层数) | 6.25 次/秒 | 可忽略 |
| **合计** | | | **≈ 6~11µs** |

结论：**CPU 侧余量极大（占 1.0ms 预算的 1% 量级）**。真正的 CPU 风险不在相变或 384 组合查表，而在三处：
1. **字符串键查找**：若规则查找使用 `string` 键（`stain_xxx`、tag 名），哈希与比较成本会放大 10~100 倍。必须在 Baker 阶段转为枚举/整数键。
2. **`AnimationCurve.Evaluate`**：`UnityEngine.AnimationCurve.Evaluate` 每次调用涉及托管对象与非内联代码，成本约为 LUT 的 20~50 倍。这也是把它排除在 Domain 之外的另一个理由。
3. **每帧分配**：`BrushCommandQueue` 出队写入 `Vector4[]` 是无分配的（`GpuCleaningSurface.cs:18-19` 预分配），但 `ReadCoverageSynchronously` 的 `new Texture2D(1,1,...)`（第 193 行）与 `DestroyOwned(pixel)`（第 198 行）是**每次同步回读一次分配 + 一次销毁**，在 4Hz 下是 4 次/秒的托管分配 + 原生纹理创建，会造成 GC 尖峰。多层化前必须改为常驻 1×1 纹理。

### 5.5 目标设备档位建议

| 档位 | 分辨率 | 最大活跃层 | Stamps/Batch | Commands/Frame | MaxPassesPerLayer | Coverage | 典型设备 | 理由 |
|---|---:|---:|---:|---:|---:|---:|---|---|
| Low | 512 | 4 | 8 | 32 | 2 | 4Hz | Android GLES3 低端（如 Snapdragon 6xx/Adreno 610 级）、iOS A11 及以下 | RT 内存 8.3MB（含归约与 Composite）；全屏 Pass ≤ 9；30 FPS 目标 |
| Medium | 768 | 6 | 12 | 48 | 4 | 6Hz | 主流中端（Snapdragon 7 系 / A13~A15） | RT 内存 33.8MB；全屏 Pass ≤ 25；60 FPS 目标 |
| High | 1024 | 6（建议，原 8） | 16 | 48 | 4 | 8Hz | 高端（Snapdragon 8 系 / A16+） | RT 内存 60.0MB；若保留 8 层则 78.7MB 超 70MB RT 预算，需 R8 归约链或半分辨率 Composite 才可放行 |

**必须实测、不能只靠推算的指标：**

| # | 指标 | 为什么不能推算 |
|---:|---|---|
| 1 | 各档位的 GPU 帧时间 P95（`Update` + `Composite` 合计） | 全屏 Blit 的实际成本受带宽、Tile 内存、带宽压缩（AFBC/ASTC）影响，桌面推算误差可达 3~5 倍 |
| 2 | 6~8 层时 `AsyncGPUReadback` 的实际回调延迟与成功率 | 移动驱动差异大；M1 已在部分设备观察到失败并触发同步兜底 |
| 3 | `SystemInfo.IsFormatSupported(R8G8B8A8_UNorm, FormatUsage.Render)` 在各真机的返回值与回退路径行为 | 必须逐机型确认，spec §7.2 已要求启动时校验 |
| 4 | 归约链的实测耗时（非等比缩放的驱动开销） | 9 级小 RT 的 Blit 固定开销远高于像素量推算 |
| 5 | 低端机同步回读路径的 GPU 停顿 | 只能真机测量 |
| 6 | 峰值内存与 12 关循环的显存趋势（spec E12-004，目标 <500MB） | 纹理压缩、驱动预留、Unity 池化行为不可推算 |
| 7 | 每层温度曲线与降频后的帧率表现 | 需要 15 分钟连续测试（spec E12-001） |

## 6. 跨平台可行性

| 项 | 现状 / 风险 | 对策 |
|---|---|---|
| 状态纹理格式 | M1 使用 `RenderTextureFormat.ARGB32` + `RenderTextureReadWrite.Linear`（`GpuCleaningSurface.cs:234`），与 spec §7.2 的 `GraphicsFormat.R8G8B8A8_UNorm` 不一致 | 改为 `GraphicsFormat.R8G8B8A8_UNorm`（用 `RenderTexture.GetTemporary`/`new RenderTexture(desc)` 的 `graphicsFormat` 字段），并在 `Initialize` 中调用 `SystemInfo.IsFormatSupported(..., FormatUsage.Render)`；不支持时回退官方可渲染 RGBA8。**通道语义在任何格式下不得改变**（spec §7.2） |

| IL2CPP 裁剪 | `CurveLut`、`StainSubtypeProfile`、效果规则均为 struct/record，无反射需求；Localization 字符串表在 M2 引入 | 保持 `Managed Stripping = Low`（spec §2.1）；不引入反射式内容加载；`ContentValidator` 只在 Editor 侧运行 |
| Shader 变体 | 单 Pass 方案不新增变体；但 `#pragma target 3.0` 下 `_Operation` 动态分支可能被展开为所有分支的并集 | 若实测显示分支代价过高，改为多 Pass 方案时，**必须**同步更新 `ProjectConfigurator.ConfigureCleaningShaderInclusion` 与 `CleaningShaderBuildGuard`，并扩充 `CleaningShaderInclusionTests` 的断言清单。**新增任何 `Hidden/SwipeClean/*` Shader 文件而不登记到 Always Included Shaders，会导致 Player 构建后 `Shader.Find` 返回 `null`，`Initialize` 走第 52~57 行的错误分支，关卡进入 `AppState.FatalError`（`PrototypeFlowController.cs:142-145`）** |
| iOS Metal | Metal 对 RT 的 `storeAction`/`loadAction` 与 `GraphicsFormat` 支持面较窄；`R8G8B8A8_UNorm` 在 iOS 上是受支持的原生格式，风险低 | 必须覆盖 iOS Metal 的 RT-002~RT-007 像素测试（spec §17.3 明确要求"至少一种 iOS Metal、Android Vulkan、Android GLES3 真机重复关键用例"） |
| Android Vulkan | URP 17.3.0 在 Vulkan 下的全屏 Blit 路径稳定，但 `AsyncGPUReadback` 在部分 Vulkan 驱动上延迟偏高 | 与 GLES3 分别验证；把两者视为两条独立路径（spec §17.7 要求同设备支持两 API 时分别验证） |
| 低端 OpenGL ES3 | 风险最高：小 RT 的 Blit 固定开销大、同步读回停顿明显、动态分支展开代价高；`R8G8B8A8_UNorm` 在 GLES3 上通常可用但需逐设备确认 | Low 档使用 512 分辨率、4 层、`MaxStampsPerBatch = 8`（spec §2.3）、`MaxPassesPerLayer = 2`；覆盖率降到 4Hz；把"GLES3 最低档可玩"作为 M2 退出条件之一 |
| 暂停与时间 | `Time.timeScale = 0f` 用于暂停（`PrototypeFlowController.Pause`），而 `GpuCleaningSurface.Update` 使用 `Time.unscaledDeltaTime` 驱动覆盖率计时器 | 相变积分**必须**使用 `BrushCommand.DeltaTime`（由输入侧按 `realtimeSinceStartupAsDouble` 计算）而非 `Time.deltaTime`，以保证暂停时不推进软化（spec §8.3"暂停时不推进" + IT-004） |

## 7. 玩法与体验风险

| 风险 | 分析 | 缓解建议 |
|---|---|---|
| "吹干了反而更难擦"的反直觉 | 本设计的核心机制是"湿物失水变成干膜：质量下降但附着上升"，这在物理上正确，但玩家看到的是"我明明处理了它，为什么更难了"。这是**最大的体验风险**，且直接影响需求文档 §2.2 的 Go/No-Go 指标（"舒服"正向反馈） | 1) 难度变化必须由**视觉**承担表达：干膜呈现为更薄、更亮、边缘更硬的反光，而非靠文字；2) 首次出现风干机制的关卡必须配置 `TutorialFlowId`（spec §5.7 已有该字段）；3) 风干不应是**必需**路径：任何关卡都必须存在"不风干也能过"的路线（构建期可达性探针验证，spec §17.6） |
| 64 种物质超出玩家可辨识度 | 玩家无法分辨"面粉"与"爽身粉"或"茶水"与"果汁"的物理差异，只会感知"松手就掉""要喷湿""黏手""会拉丝""有颗粒"等手感 | 提出**降维假设：玩家只感知 6~8 组手感**。建议的分组：①干散粉（气吹/刷）②颗粒硬物（沙、糖粒，带 ScratchRisk）③油脂膜（需去油）④低黏液体（吸水）⑤黏稠膏体（需先湿后擦）⑥胶类（需溶剂）⑦干膜糖渍（需软化等待）⑧硬水垢（需酸性）。**这 8 组恰好可与子类体系一一映射**，因此 64 种物质在玩法层的真实表达量是 8 组 × 参数差异，UI 与教学只需覆盖 8 组 |
| 14 个子类的提示系统覆盖 | `WrongToolHintCooldown = 2s`（spec §8.4）已定义触发节奏，但提示文案来自 `EffectRule.HintKey`（本地化键） | 14 子类 × 6 工具的提示在玩法上只需 **8 组 × 3~4 条**（"该用 XX"）；键数量估算约 30 条，可维护。若按 64 物质各写一条提示则为 64+ 条，不推荐（且违反 spec §8.4"不在代码拼接污渍名"） |
| 速干胶时间窗与 ADR-009 的张力 | 时间窗机制天然产生"错过窗口"的失败感 | 时间窗只放大难度不阻断完成（§3.7）；`FastCureAdhesive` 在 64 项清单中仅 1 项（`stain_super_glue`），建议**首版不放时间窗**，或仅用于高难度后期关卡 |
| 相变是否让玩家困惑"什么时候该吹干" | 双向可逆意味着"吹干"不是必须动作，玩家可能永远不用该工具 | 风干/暖风机的价值必须落在**可量化的收益**上：例如"吸水纸只能吸表面水，湿膜残留会导致擦拭拖出 WaterMark；先风干再擦可避免水痕"。即用 spec §8.4 的 WaterMark 惩罚反向定义风干的价值 |
| 相变的可读性 | 相态是连续量而非二值，玩家可能看不出"现在是干还是湿" | 复用 spec §8.3 的表达要求（光泽、边缘、泡沫、颜色变化），并确保"状态不只靠颜色"（需求文档 E12-008 的可访问性要求） |
| 相变增加操作步数是否破坏"解压"定位 | 三步操作（喷→等→擦）比一步"用力擦"更复杂 | 教学曲线必须保证 M1 的"干布直擦"路径在第 1~2 关仍然有效（spec §10.10 的 12 关矩阵第 1 关为"指纹弱化变体+布"），相变从第 4 关（油+喷雾）才开始引入 |

| 崩溃与回读失败率 | 外测统计 | 崩溃会话 <0.5%（E12-005）；回读失败 <1% |

## 11. 结论与建议

### 11.1 分阶段实施建议

**建议先做的 12 种物质**（覆盖全部 8 组手感，且与 spec §10.10 的 12 关矩阵前 10 关对齐）：

| 批次 | 物质 ID | 子类 | 对应手感组 | 对应关卡（spec §10.10） |
|---:|---|---|---|---|
| 1 | `stain_fingerprint_oil` | OilFilm | ③油脂膜 | 1 |
| 2 | `stain_dust_fine` | LoosePowder | ①干散粉 | 2 |
| 3 | `stain_water_drop` | LowViscosityLiquid | ④低黏液体 | 3 |
| 4 | `stain_cooking_oil_film` | OilFilm | ③油脂膜（厚） | 4 |
| 5 | `stain_flour_powder` | LoosePowder | ①干散粉（细） | 5 |
| 6 | `stain_mud_slurry` | CompositeSludge | ⑤黏稠膏体 | 6 |
| 7 | `stain_sand_grain` | LoosePowder | ②颗粒硬物（ScratchRisk） | 7 |
| 8 | `stain_sugar_dry` | SugarFilm | ⑦干膜糖渍 | 8 |
| 9 | `stain_oil_cooking` | OilLiquid | ③油脂膜（液体） | 9 |
| 10 | `stain_water_scale` | SaltCrystal | ⑧硬水垢（acid） | 隐藏/进阶 |
| 11 | `stain_ink_dry` | InkPigment | ⑥胶类/溶剂组（alcohol） | 11（隐藏污渍） |
| 12 | `stain_super_glue` | FastCureAdhesive | ⑥胶类（solvent，可选时间窗） | 12 |

**建议先做的操作**（按依赖顺序）：

1. `Clean`（已有）；
2. `AddMoisture`（相变入口，`G += moisture*influence*dt`，R 不变）；
3. `Absorb`（相变出口，兼作风干/暖风机的语义载体）；
4. `Smear`（油/泥的错误路径，spec §8.4 的 WaterMark 来源）；
5. `Push`（灰尘/沙粒的气吹路径）；
6. `Reveal`（UV 专用，走 `UvInspectionController`，不写状态纹理）。

**建议先做的溶剂档位**：`degreaser`（食用油/护肤霜/鼻油）与 `solvent`（白乳胶/贴纸胶/口香糖残胶）两档，落在喷雾工具上。`acid`/`enzyme`/`acetone` 延后。

### 11.2 可以开始 / 需要先做 PoC / 不建议做

| 条目 | 判定 | 依据 |
|---|---|---|
| `StainPhase` + `StainSubtype` 枚举与 `LegacyCategory` 映射 | **可以开始** | 不破坏既有 30 组合（§3.1） |
| `StainSubtypeProfile` / `StainPhaseProfile` 纯数据记录 | **可以开始** | Domain 无 Unity 依赖，纯 struct/record |
| `CurveLut` + Baker（AnimationCurve → LUT） | **可以开始** | 是 M2 的硬前置（§3.5） |
| `ContentValidator` 的 384 组合穷举 | **可以开始** | 必须在内容量产前完成 |
| `StainUpdateScheduler` 稳定分组 + `MaxPassesPerLayer` | **可以开始** | M1 已具备改造基础（§3.4 的 S2） |
| `MaxStampsPerBatch` / `MaxCommandsPerFrame` 改为档位注入 | **可以开始** | 当前是 `const`，与 spec §2.3 冲突 |
| 通道复用（B 通道编码相态） | **可以开始，但需视觉走查** | 8 位量化在扰动表现上可能可见条带（RISK-STAIN-001） |
| 相变机制（软化 + 回干 + 相态乘子） | **需要先做 PoC-1** | 体验风险最高（RISK-STAIN-006） |
| 每帧 Pass 上界与帧时间 | **需要先做 PoC-3** | 只能实测，推算误差可达 3~5 倍（§5.5） |
| 覆盖率 1×N 多层汇总 + 常驻 1×1 同步纹理 | **需要先做 PoC-5 + PoC-3** | 移动端驱动差异大（RISK-STAIN-011） |
| 1024 分辨率 × 8 层 | **不建议做** | 78.7MB 超 spec §16.3 的 70MB RT 预算（§5.1） |
| 双 RT（独立相态纹理） | **不建议做** | 1024 档内存不可接受（§3.2） |
| 每操作一个独立 Shader 文件 | **不建议做** | 必须同步登记 Always Included，构建风险高（RISK-STAIN-010） |
| 6 个溶剂独立工具（acid/degreaser/enzyme/solvent/alcohol/acetone 各一） | **不建议做（M2/M3）** | 类别组合由 30 增至 66，UI 与验证面翻倍（§3.5） |
| 采样真实照片制作遮罩 | **不建议做** | 授权链条与 E11-F03 冲突（§4.2） |
| 速干胶时间窗（首版） | **不建议做** | 与 ADR-009 张力最大（RISK-STAIN-005） |
| 64 种物质一次性全量上线 | **不建议做** | 32~128 人日；应先 12 → 24 → 64（§4.1、§8） |

### 11.3 需要主策 / 主程拍板的决策点

| # | 决策点 | 选项 | 影响面 |
|---:|---|---|---|
| D-1 | High 档（1024）的最大活跃层数是 6 还是 8 | ①降为 6（修改 spec §2.3）②保留 8 并把归约链改 R8 单通道 ③保留 8 并把 Composite 降为半分辨率 | 内存预算、视觉锐度、spec §2.3 一致性的取舍 |
| D-2 | 相态在状态纹理中的编码位置 | ①B 通道高半段（推荐）②A 通道存相态 + WaterMark 独立层 | 涂抹表现精度、WaterMark 实现成本 |
| D-3 | `InorganicScale` / `AdhesiveResidue` 是否从预留子类升为实际子类 | ①保持预留 ②迁移 5 项物质 | 枚举序列化值、子类规则数量 |
| D-4 | 溶剂档位是否落地，落几档 | ①`degreaser`+`solvent` 两档 ②六档全上 ③不做溶剂，用工具区分 | 喷雾 UI 复杂度、30 组合验证不变性 |
| D-5 | 风干/暖风机是独立工具还是喷雾/吸水纸的档位 | ①独立工具（+1 工具类别）②吸水纸档位 | `IToolStrategy` 实现量、HUD 布局 |
| D-6 | 速干胶时间窗是否进入首版 | ①不进 ②仅在后期关卡进 ③全量进 | ADR-009 可恢复性承诺 |
| D-7 | 玩法层是否公开采用"8 组手感"降维 | ①公开采用 ②保持 14 子类的玩家可见性 | 教学内容量、UI/图鉴设计 |
| D-8 | 64 种物质是否全部进入正式包 | ①全部 ②首批 36 种（Dry）分 M3/M4 两批 ③按关卡需要裁剪 | 包体（`当前关卡资产 120MB 上限`，spec §16.3）、量产工时 |
| D-9 | 相变是否需要"流挂"表现（边缘/斜面） | ①做（按画质降级，Low 关闭）②不做，仅规则层 | 表现层 Pass 数、Low 档一致性 |
| D-10 | 命名口径："相态"是否作为对外可宣传的玩法卖点 | ①是（商店文案需一致）②仅内部技术命名 | 商店表述（spec §15.4 与 REL-001） |
